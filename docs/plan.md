## 1. 要件の理解

構築するのは、ユーザーが通常どおりClaude Codeを起動して自然言語で依頼するだけで、Claudeが要件整理・計画・委譲・レビュー・報告を担い、コード変更・テスト実行をローカルのCodex CLIへ自動委譲する個人用クロスハーネスである。特徴は次の5点。

1. Claude=司令塔(読み取り・計画・委譲・検証・報告)、Codex=実行役(実装・テスト・コマンド実行)の固定役割分担。再依頼回数に上限を設ける。
2. 両者ともサブスクリプション認証のみを使用し、API従量課金経路を構成・運用の両面で遮断する(フェイルクローズ)。
3. モデル・effort・役割配置・並列数・再試行・タイムアウト等はホームディレクトリの個人設定で管理し、プロジェクトは品質基準・禁止事項・テスト要件のみを定義できる。
4. セットアップ後は専用コマンド・接頭辞・手動切り替えなしで全プロジェクトに常時適用される。
5. モデル出力・ターミナル出力・コンテキスト消費を、フェーズ分離・ファイル受け渡し・ログ退避と要約・段階的読み込みで最小化する。

ECCの設計思想(single source of truth+薄いアダプター、コンテキスト経済、逐次フェーズ、最小並列化)を参考にするが、資産の移植は行わず必要なパターンのみを抽出する。

## 2. 実現可能性の判定

分類は「公式機能で実現可能/アダプターやHookで実現可能/指示ベースでのみ実現可能/一部のみ実現可能/現時点では実現不可」の5区分。保証水準の異なる下位項目が併存する要件は「一部のみ実現可能」とし、内訳を根拠欄へ記す。ECC由来の語彙(Native / Adapter-backed / Instruction-backed)を適宜併記する。

| # | 要件 | 判定 | 根拠・補足 |
|---|---|---|---|
| 1a | Claude→Codexの委譲実行そのもの | アダプターやHookで実現可能(Adapter-backed) | Claude CodeのBashツールから`codex exec`を呼ぶ経路は公式機能の組み合わせ【公式】。委譲判断・指示作成は指示ベース |
| 1b | 「Claudeはコードを変更しない」の徹底 | 一部のみ実現可能 | PreToolUse hookでEdit/Writeを検知・確認要求まではネイティブに可能【公式】。原則の遵守自体はモデルの指示追従に依存(Instruction-backed) |
| 1c | 再依頼回数の上限・ループ防止 | アダプターやHookで実現可能 | 委譲を専用ラッパー経由に一本化し、ラッパーが試行回数・同一失敗を状態ファイルで数えて拒否する設計 |
| 2 | ECC参考(採用/変更/不採用の区分) | —(調査・方針要件のため5区分の対象外) | 本節末尾の採用区分表で採用可否と実現手段を示す。ECCそのものへの依存は持たない |
| 3 | サブスクリプション枠のみ使用 | アダプターやHookで実現可能 | 大部分は公式機能で、環境遮断・認証確認をアダプターが担う。詳細は下記「重点判定A」 |
| 4 | 個人ごとのモデル・effort設定 | アダプターやHookで実現可能 | モデル/effort指定は公式機能、ハーネス横断の役割配置は自作設定層が担う。詳細は下記「重点判定C」 |
| 5 | コマンドなしの常時適用 | 一部のみ実現可能 | 詳細は下記「重点判定B」 |
| 6 | モデル出力トークン抑制 | 指示ベースでのみ実現可能 | Claude Codeに出力トークンを直接制限する公式設定は見当たらない【未確認】。報告書式の固定は指示ベース、受け渡しは`--output-schema`等でネイティブ寄りに安定化【公式】 |
| 7 | ターミナル出力削減 | アダプターやHookで実現可能 | ラッパーが全文ログをファイルへ退避し要約のみ返す。Claude側は`BASH_MAX_OUTPUT_LENGTH`等の公式設定あり【公式】 |
| 8 | コンテキスト消費抑制 | 一部のみ実現可能 | 常時読み込み最小化・skillのlazy load・subagent独立コンテキストはネイティブ【公式】。フェーズ分離・1入力1出力の規律は指示ベース |
| 9 | モデルルーティング | アダプターやHookで実現可能 | 個人設定ファイル+ラッパーのCLI上書き(`-m`、`-c`、`--profile`)で実現【公式】。昇格判断は指示ベース+ラッパーの機械的規則 |
| 10 | 安全性と再帰防止 | アダプターやHookで実現可能 | Codexの`[agents]`のmax_threads/max_depth、sandbox_mode、hooksはネイティブ【公式】。Codex→Claudeの入れ子起動禁止は環境マーカー+両側hook、未コミット変更の保護はラッパーの事前確認で担保(第5節) |

### 重点判定A: API課金なし(要件3)

- `codex exec`は保存済みのChatGPT認証(`~/.codex/auth.json`)をそのまま再利用する【公式】。ChatGPT認証からAPI課金へ「自動で切り替わる」仕様は公式ドキュメントに存在しないことを確認した【公式】。APIキー課金は`CODEX_API_KEY`の設定やAPIキーによる明示的なログイン操作をした場合のみ。
- レート上限到達時も、進行中ターン完了後は「リセット待ち/クレジット購入/ユーザーが明示的にAPIキーへ切替」の3択であり自動遷移はない【公式】。
- 残存リスクは2つ。(1)`OPENAI_API_KEY`環境変数とChatGPTログインの優先順位は公式に明文がなく、環境変数が黙って優先されたというバグ報告(openai/codex issue #15151)がある【未確認】。(2)Claude側は`ANTHROPIC_API_KEY`が存在するとAPIキー認証が優先される【公式(詳細優先順位は部分確認)】。
- 対策(フェイルクローズ): 委譲ラッパーは子プロセス環境を許可リスト方式で構築しAPIキー系環境変数を一切渡さない。加えて`~/.codex/config.toml`で認証方式をChatGPTへ固定する公式キー(`forced_login_method`)を有効にする【公式】。セッション開始時とラッパー実行時に認証状態を確認し(`claude auth status`相当、`codex login status`相当【公式】)、認証不明・APIキー検出・上限到達のいずれでも委譲を停止する。
- 結論: アダプターやHookで実現可能(大部分は公式機能)。ただし「非対話実行でサブスク認証が維持されること」の最終保証は実機検証(実装フェーズP1)で確認し、それまでは【未確認】として扱う。

### 重点判定B: 常時適用(要件5)

- 読み込みの保証: `~/.claude/CLAUDE.md`は全プロジェクトで自動読み込み【公式】。ユーザーレベルskill(`~/.claude/skills`)はdescriptionのみ常駐し本文はlazy load【公式】。ユーザーレベルhooks(`~/.claude/settings.json`)は全プロジェクトで発火【公式】。Codex側も`~/.codex/AGENTS.md`が全実行で自動読み込み【公式】。よって「司令塔ルール・実行役ルールが毎回読み込まれる」ことは公式機能で保証可能。
- 遵守の保証: 「読み込まれた指示に常に従う」ことはLLMの性質上保証できない(Instruction-backed)。保証可能な範囲=読み込み・hookによる機械的ガード(認証確認、委譲経路の一本化、Edit/Write検知)。保証できない範囲=委譲判断の的確さ、報告書式の完全遵守。後者はhookの機械検査と運用観察で補強する。
- 結論: 一部のみ実現可能(読み込みと機械的ガードは公式機能、判断遵守は指示ベース)。

### 重点判定C: ClaudeからのCodex自動実行と個人別モデル設定(要件1・4)

- Codex自動実行: Bashツール経由の`codex exec`呼び出しは、permissions設定でラッパーコマンドをallowに登録すれば確認プロンプトなしで実行できる【公式】。非対話実行の既定sandboxはread-onlyで、書き込みは明示指定が必要【公式】。ラッパーが役割に応じてsandboxを指定する。
- 個人別モデル設定: Claude側はユーザーsettings.jsonの`model`と`effortLevel`、subagent定義(`~/.claude/agents`)のfrontmatterで役割別に指定可能【公式】。Codex側は`~/.codex/config.toml`の`model`と`model_reasoning_effort`、agent定義(`~/.codex/agents`)で役割別に指定可能【公式】。ハーネス横断の役割配置・並列数・再試行・タイムアウト・読み書き・出力上限・委譲可能タスク種別は両ハーネスに共通機構がないため、個人ハーネス設定ファイル(新設)+ラッパーで実現する(Adapter-backed)。
- 結論: いずれもアダプターやHookで実現可能(モデル/effort指定自体は公式機能)。横断項目のみ自前の設定層が必要。

### ECC設計の採用区分(要件2)

そのまま採用(理由: ハーネス非依存で目的に直結):

| 項目 | 内容 |
|---|---|
| 中間成果物のファイル受け渡し | 「各フェーズは1つの明確な入力と1つの明確な出力」原則。クロスハーネスでは会話コンテキストを共有できないため事実上必須 |
| Iterative Retrieval | 収集→関連度評価→条件更新のループを最大3サイクル、十分な関連ファイルが揃えば早期終了 |
| 対応度の語彙 | Native / Adapter-backed / Instruction-backed / Reference-only の4区分を本計画の判定語彙として使用 |
| 最小並列化 | 逐次を既定とし、並列は独立作業のみ。renai既存ルール(最大3子スレッド・深さ1)とも整合 |
| MCP最小化基準 | 「全ユーザー普遍性+ステートフル必然性」を満たすものだけ常駐。statelessな用途はCLI利用のskillへ |

変更して採用(理由: 実行役をClaude subagentからCodexへ置換する等の適合が必要):

| 項目 | 変更点 |
|---|---|
| 逐次5フェーズ(RESEARCH→PLAN→IMPLEMENT→REVIEW→VERIFY) | フェーズ構成は流用し、IMPLEMENT/テスト実行をCodexへ、RESEARCH/PLAN/REVIEWをClaudeへ割り当て直す |
| 役割別モデル3層(深い推論/標準/安価) | 概念を採用し、モデル名は現行のClaude系(fable/sonnet/haiku)とCodex系(gpt-5.6-sol/terra/luna)へ置換 |
| AGENTS.mdマーカーブロックのadd-onlyマージ+バックアップ | 手法のみ移植し、対象は`~/.codex/AGENTS.md`1ファイルに縮小 |
| セッション状態の保存・復元 | Stop保存/SessionStart復元の2フックに絞り、注入量上限(数千字)を設ける |
| 知識のskill昇格 | フル自動学習基盤は導入せず、「複数プロジェクトで反復した知見を手動レビュー経由でskill化する」軽量運用のみ採用 |

採用しない(理由: 目的外・保守負債・方針矛盾):

| 項目 | 理由 |
|---|---|
| 267 skills / 67 agentsのカタログ | 常時コンテキスト税と管理コストが目的に見合わない |
| Cursor/OpenCode等の他ハーネスアダプター | 対象はClaude Code+Codexの2つのみ |
| Dashboard等の周辺プロダクト、重量級マルチサービス並列 | 目的(委譲実行)に無関係、最小並列化方針と矛盾 |
| ECCの`.codex/config.toml`同梱MCP群 | ECC自身のMCP最小化ポリシーと矛盾しており採らない |

注意: ECCのCompliance Matrixは「Codexのhooksは指示ベースのみ」とするが、現行Codex公式ドキュメントにはネイティブhooks(SessionStart/PreToolUse/PostToolUse/Stop等、exit code 2でブロック可)が存在する【公式】。本計画はECC文書ではなく現行公式仕様を優先する。

## 3. 推奨アーキテクチャ

方針: 新しい常駐プロセスやルーターを作らず、(1)Claude Codeのユーザーレベル資産(CLAUDE.md・skill・agents・hooks・settings)、(2)Codexのユーザーレベル資産(AGENTS.md・config・agents・hooks)、(3)両者をつなぐ唯一の委譲経路である「委譲ラッパー」(単一の実行スクリプト)、(4)個人ハーネス設定ファイル、の4点で構成する。資産一式は私有の「個人ハーネスrepo」で版管理し、導入スクリプトでホームディレクトリへ配置する。

```
ユーザー
  │ 自然言語の依頼(通常のClaude Code起動のみ)
  ▼
Claude Code(司令塔)…サブスクリプション認証
  ├─ ~/.claude/CLAUDE.md            … 司令塔憲章(短い常時読み込み)
  ├─ ~/.claude/skills/(司令塔skill) … フェーズ手順・委譲規則(lazy load)
  ├─ ~/.claude/agents/              … Claude側役割(探索・レビュー等)
  ├─ ~/.claude/settings.json        … hooks(認証確認・ガード)+permissions
  │
  │ 作業指示ファイル(タスク毎の実行ディレクトリへ書き出し)
  ▼
委譲ラッパー(唯一のCodex呼び出し経路)
  ├─ 個人ハーネス設定(役割→ハーネス/モデル/effort/上限)を解決
  ├─ 環境を許可リスト方式で構築(APIキー系変数を遮断)
  ├─ 認証状態を確認(不明ならフェイルクローズ)
  ├─ 作業ツリーの未コミット変更を検出(既定は停止、設定で分離実行)
  ├─ 試行回数・タイムアウト・同一失敗を管理
  ▼
codex exec(実行役)…ChatGPTサブスクリプション認証
  ├─ ~/.codex/AGENTS.md             … 実行役憲章(全実行で自動読み込み)
  ├─ ~/.codex/config.toml           … 認証固定・既定モデル
  ├─ ~/.codex/agents/*.toml         … Codex側役割定義
  └─ sandbox(役割に応じread-only / workspace-write)
  │
  │ 差分・テスト結果・最終メッセージ(ファイル)
  ▼
実行ディレクトリ(タスク毎の一時領域)
  ├─ 作業指示 / イベントログ全文 / 最終メッセージ
  ├─ 差分サマリ / テスト結果サマリ / 試行状態
  ▼
Claude Code(司令塔)が要約のみ読み取り、差分と完了条件を検証
  │
  ▼
ユーザーへの最終報告(変更内容・検証結果・未解決事項)

[プロジェクト層(リポジトリ側)]
  AGENTS.md、.codex/config.toml・harness.toml・agents/、docs/ 等
  … 品質基準・checks・禁止事項を定義。個人のモデル選択と認証は上書き不可
```

関係の要点:

- 共有ルールの一次配置は各ハーネスのネイティブ位置(`~/.claude/CLAUDE.md`と`~/.codex/AGENTS.md`)とし、重複する規範(報告書式、再帰禁止、秘密情報の扱い)は個人ハーネスrepo内の単一ソースから導入スクリプトが両方へ反映する(ECCのsingle source of truth+薄いアダプター)。
- Claude→Codexの受け渡しは常にファイル経由。会話履歴・思考過程は渡さず、作業指示ファイルには目的・対象範囲・制約・完了条件・参照ファイルのみを含める。
- ログは全文をタスク毎の実行ディレクトリへ保存し、モデルへは要約と参照パスだけを返す。不足時のみ該当範囲を段階取得する。
- 認証確認はセッション開始時(hook)とラッパー実行時の二重で行い、結果を短期キャッシュする。

## 4. 設定の責務分担

### 責務の分割

- Claude Code側: 司令塔の判断規範(分類・委譲・検証・報告)、Claude側役割のモデル/effort、hooksによる機械的ガード、permissions。
- Codex側: 実行役の行動規範(最小差分・報告書式・質問禁止・再委譲禁止)、Codex側役割のモデル/reasoning effort、sandbox既定、認証方式固定。
- 両者で共有する部分: 報告項目の定義、再帰禁止・秘密情報禁止などの安全規範、中間成果物の置き場所の規約。個人ハーネスrepoを単一ソースとし、導入スクリプトが両側の設定へ反映する。
- ユーザー個人設定: モデル・effort・役割配置(どの役割をどちらのハーネスで実行するか)・並列数・再試行・タイムアウト・読み書き・出力上限・委譲可能タスク種別・認証。すべてホームディレクトリ配下。
- プロジェクト共有設定: 品質基準、必須check、禁止事項、テスト要件、ドメイン知識(renaiでは再設計後のルートAGENTS.md、各領域のnested AGENTS.md、`verify:<area>`複合script。第15節)。
- プロジェクト固有の個人設定: 特定リポジトリでのみ適用したい個人差分(`.claude/settings.local.json`等、および個人ハーネス設定内のプロジェクト別節)。
- 実行時に生成される一時情報: タスク毎の実行ディレクトリ(作業指示、ログ全文、要約、試行状態)、セッション状態ファイル、認証確認キャッシュ。保持期間を定めて自動削除する。

### 優先順位とマージ規則

ネイティブのマージ規則(Claude: managed>local>project>user、Codex: CLI上書き>プロジェクト>ユーザー)はそのまま活かしつつ、要件「プロジェクトが個人のモデル選択・認証を上書きできない」はキー所有権で実現する。すなわち実効設定を組み立てるのは委譲ラッパーと司令塔skillであり、次の規則を強制する。

1. 安全強制(最優先・緩和不可): APIキー経路遮断、再帰禁止、sandbox既定、秘密情報の不通過。個人ハーネスrepoに同梱され、設定では無効化できない。
2. モデル・effort・並列数・認証に関するキー: 個人層のみが決定権を持つ。プロジェクト側に同種の指定があっても、ラッパーはCLI上書き(`-m`等)で個人設定を優先する。プロジェクトの役割定義を尊重したい場合のみ、プロジェクト固有の個人設定で明示的に委任できる(既定は個人優先)。
3. 品質基準・check・禁止事項・テスト要件: プロジェクト層が個人層より優先する(強化方向のみ。安全強制の緩和は不可)。
4. その他の一般キー: ネイティブの優先順位に従う。

## 5. オーケストレーション手順

状態遷移の全体像(すべての規模で共通の骨格):

```
受信 → 分類 → (調査) → 計画 → 委譲実行 → 検証 → (再修正ループ) → 報告
                                     ▲              │
                                     └── 上限内の再依頼 ──┘
```

共通の前処理: セッション開始時にhookが認証状態と前回セッションの短い状態を注入する。依頼受信後、司令塔は(1)コード変更を伴うか、(2)規模(小/中/大)、(3)委譲可能タスク種別に該当するか、を判定する。コード変更を伴わない質問・調査はClaude単独で完結し、Codexを起動しない。また、コード変更を伴う委譲の前にラッパーが作業ツリーの未コミット変更を検出し、存在する場合は既定で停止してユーザーへ確認する(個人設定によりworktree分離での実行へ切り替え可能)。ユーザー由来の未コミット変更を委譲差分へ混入・消失させない(要件10のGit保護)。

### 小規模(2ファイル以内・要件明確・設計判断なし・高リスク領域を含まない)

1. 司令塔が調査サブエージェントなしで対象を確認し(必要最小限の読み取りのみ)、作業指示ファイル(目的・対象範囲・制約・完了条件・参照ファイル)を実行ディレクトリへ作成する。
2. ラッパー経由でCodex(implementer役、workspace-write)を1回起動する。
3. ラッパーが差分サマリ・テスト結果・最終メッセージをファイルで返す。
4. 司令塔が差分と完了条件を照合し、プロジェクトの必須checkの結果を確認して報告する。

### 中規模(複数ファイル・設計判断あり・単一領域)

1. 調査: Claude側explorer(read-only)またはCodex explorer(read-only)が担当(ルーティングは第6節)。Iterative Retrievalを最大3サイクルとし、調査の全履歴ではなく短い調査結果ファイルだけを次工程へ渡す。
2. 計画: 司令塔が実装方針を確定し、棄却案を含めない作業指示ファイルを作成する。
3. 実装: Codex implementerへ委譲(workspace-write)。
4. テスト: 同一Codexセッションのresume、またはtester役で関連テストのみ実行。
5. レビュー: 司令塔が差分・テスト結果を検証。大きな変更や高リスク領域はレビュー役(第6節)を追加する。
6. 報告: 変更内容・検証結果・未解決事項のみ。

### 大規模(複数領域・多数ファイル・長時間)

1. 調査・計画は中規模と同じだが、計画段階で独立した作業単位へ分解し、単位ごとに完了条件を定義する。
2. 作業単位を逐次実行する(各単位は中規模ループ)。相互に独立な単位のみ、上限2並列までworktree分離で並列化してよい。
3. 単位ごとに司令塔が検証し、全単位完了後に統合検証(プロジェクトの必須check全体)を行う。
4. 各作業単位の完了時にコンテキスト使用率を確認し、閾値(第7節。初期値70%、個人設定で変更可)を超えていたら進捗状態を短く保存し、新しいセッションで状態ファイルから再開する。

### 失敗時

1. テスト失敗・レビュー指摘の場合、司令塔は要約から原因を特定する。不足時のみログ全文の該当範囲を段階的に取得する。
2. 修正方針を作り、対象を限定した再依頼をresumeで行う(既定上限2回、個人設定で変更可)。
3. 同一失敗シグネチャ(同一テスト・同一エラー種別)を2回検出したら、再試行を打ち切りモデル/effortを1段昇格して1回だけ再実行する。
4. それでも失敗する場合は停止し、状態を保存したうえで、原因・試行履歴・選択肢をユーザーへ報告する。
5. レート上限到達・認証異常は即時停止して報告する(自動待機や課金経路への迂回はしない)。
6. 中断時(ユーザー割り込み・タイムアウト)はラッパーが子プロセスを終了し、実行ディレクトリに中断マークを残す。次回セッション開始時に孤児ディレクトリを掃除する。

## 6. モデルとeffortのルーティング

前提(2026-07時点の確認結果): Claude側サブスクリプションではfable(Claude Fable 5)、sonnet(Sonnet 5)、haiku(Haiku 4.5)等のエイリアスとeffort(low/medium/high/xhigh/max)が利用可能【公式】。Codex側ChatGPTサブスクリプションではgpt-5.6-sol(深い推論)、gpt-5.6-terra(標準)、gpt-5.6-luna(安価・反復向き)とreasoning effort(minimal/low/medium/high/xhigh)が利用可能【公式】。これらは変動するため、初期値は個人ハーネス設定に置き、コードへ埋め込まない。

初期ルーティング(すべて個人設定で変更可能。現在のユーザー設定=Claude親fable[1m]/xhigh、Codex既定sol/highを尊重した提案):

|---|---|---|---|

## 8. 認証と課金防止

- サブスクリプション使用の確認方法: セッション開始hookがClaude側の認証状態を確認し(認証状態確認コマンドの結果のみ利用)、委譲ラッパーが初回実行時にCodex側の`codex login status`相当で認証方式を確認する【公式】。確認結果(認証済み/方式)は当日内キャッシュし、値そのものは表示しない。
- APIキー経路の拒否: (1)ラッパーは子プロセス環境を許可リスト方式で構築し、`OPENAI_API_KEY`・`CODEX_API_KEY`・`ANTHROPIC_API_KEY`等を伝播させない。(2)`~/.codex/config.toml`に認証方式をChatGPTへ固定するキー(`forced_login_method`)を設定する【公式】。(3)セッション開始hookがシェル環境にAPIキー系変数を検出した場合、警告を注入し委譲を停止する。環境変数の優先順位が公式に未保証である問題(第2節・重点判定A)への防御。
- 認証切れ時の挙動: ラッパーは認証未確認のままCodexを起動しない。認証切れを検知したら委譲を停止し、進行中の状態を保存し、ユーザーへ再ログインを依頼する。自動再認証・認証情報の生成・コピーは行わない。
- 誤課金を防ぐ停止条件(いずれか成立で委譲停止・ユーザー報告): 認証状態が不明/認証方式がChatGPT・サブスクリプション以外/APIキー系環境変数を検出/レート上限到達/設定ファイルに未知の認証関連変更を検出。停止は安全側(fail-close)であり、課金方式が不明な経路への自動フォールバックは存在しない。
- 禁止事項: `~/.codex/auth.json`・`.env`系・keychainの内容を読まない・表示しない・ログや中間成果物へ書かない。認証ファイルはバックアップ対象からも除外する(存在確認のみ許可)。
- 実機検証(実装フェーズP1で必須): 独立CLI導入後、read-onlyの小タスクを非対話実行し、(1)実行がChatGPT枠の消費として記録されること、(2)APIキー無しで完走すること、(3)APIキー系変数を意図的に与えた場合にラッパーが拒否すること、を確認する。確認完了までは要件3の充足を【未確認】として扱う。

## 12. リスクと制約

技術的制約・公式仕様上の制約:

- 指示遵守は確率的: 常時適用で保証できるのは「読み込み」と機械的ガードまで。委譲判断・書式遵守は逸脱しうる(検出はhookと運用観察で補強)。
- Claude側に出力トークンを直接制限する公式設定が見当たらない【未確認】: 出力削減は指示+受け渡し構造に依存。
- `codex exec`のexit code体系が未文書【未確認】: ラッパーはexit code以外(最終メッセージ・イベント)も併用して成否判定する。
- VS Code拡張同梱CLIのターミナル利用は公式手順なし【未確認】: 独立CLIを別途導入する(P1)。CLIと拡張が認証情報を共有することは公式に明記されている【公式】が、導入後の再ログイン要否はP1で実機確認する。
- AGENTS.mdの読み込みは既定32KiB上限【公式】: 実行役憲章は短く保つ。
- reasoning effortの最上位段(Max/Ultra表記)のconfig値対応は未確認【未確認】: 初期値はxhighまでを使用。

認証上の制約:

- `OPENAI_API_KEY`とChatGPTログインの優先順位が公式未保証+優先されたバグ報告あり【未確認】: 環境変数遮断と認証固定キーで防御(第8節)。
- `~/.codex/auth.json`は平文の資格情報【公式】: 読み取り・複製・バックアップ対象化を禁止。
- サブスクリプション自動実行の制限【制限あり】: 非対話実行はレート枠(5時間ウィンドウ+週次上限)内でのみ動作し【公式】、上限到達で停止する。長時間の自動運転や大量並列は枠を急速に消費する。本構成は1タスク=Claude枠+Codex枠の二重消費であり、単純タスクでは従来より総消費が増える可能性がある(第11節で測定)。

保守性・セキュリティ・環境差:

- 両CLIの更新頻度が高い(hooksとsubagentは比較的新しい機能): バージョン更新で設定キー・挙動が変わる破損リスク。対策: 個人ハーネスrepoで版管理し、P0のインベントリとdoctor系診断を定期実行、更新はピン留めと段階適用。
- Codex側hooksの粒度・matcher仕様はClaude Codeと完全同等ではない可能性【未確認】: 入れ子起動ガードはhook・環境マーカー・憲章の三重で実装し、hook単独に依存しない。
- OS差異: 本計画はmacOS前提。sandbox実装はOSごとに異なり【公式】、通知などの周辺手段もOS依存となる。
- プロジェクトハーネスとの整合: renaiのリポジトリ層はPR#647の再設計決定(第15節)により、Codex親を必須とする統治機構を撤去し、ハーネス中立の規約(TaskSpecの縮約表示(第15節の正規化方式追補)、blocking unknownのみ質問、`verify:<area>`実行)へ移行する。これにより個人層(Claude親)との構造的矛盾は解消される見込み。リポジトリ側の品質基準・安全規則は引き続きそのまま尊重し、個人層は「実行の力学(誰がどのモデルで実行するか)」のみを担う。将来矛盾が再発した場合はリポジトリ規約を優先し、個人層の該当機能を無効化できる構造にする。
- ECC情報の鮮度: ECCの対応表はCodexネイティブhooks登場前の記述を含む。設計判断は常に現行公式ドキュメントを一次情報とする。

## 15. renaiリポジトリ層の再設計決定(PR#647)と本計画への影響

### 決定事項

| 論点 | 決定 |

### 正規化方式の追補(2026-07-17決定)

TaskSpec規約の具体形を次のとおり決定した(トークン削減と、Claude親でも成立するハーネス中立化のため)。

- explorer preflightを廃止し、親が自己正規化する。「親は6項目を自ら初期生成しない」規則も削除する。理由: preflightはrepository調査を行わず原文を並べ替えるだけで情報増がなく(親のコンテキストに原文が既にあるため往復分の純増)、gpt-5.6-terraへの委譲はClaude親では実行不可(Daccho blocker(2))。「明示された意図・制約を推論で置き換えない」原則はテキスト規約として保持する。
- 表示は`goal`(1行)と`done_when`(最大3件・各1行)を常設とし、`assumptions`(根拠付き)と`unknowns`は存在する場合のみ併記、空の項目は表示しない。表示量をsmall/complex分類ではなく「書くべき判断が存在するか」に比例させる。`context`と`constraints`は表示から除外する(モデルが調査して適用する入力であり、ユーザーが検証すべき判断ではない。委譲時の参照情報は作業指示ファイル側が担う)。
- 依頼文にある内容を復唱せず、解釈・補完した差分だけを書く。表示は分類と調査の完了後に1回だけ行う。
- blocking unknownのみ質問して停止し、他は根拠付きassumptionで続行する規則は不変。正規化中にblocking unknownが出た依頼は`small`として扱わない。

## 17. ハーネス対称性の調査結果と是正計画(2026-07-18)

2026-07-18、ロールのmodel・effort・harnessを双方向に設定可能にする変更を
行った。しかし、対称化されたのは実行役の起動経路のみであり、その周辺は依然として
Codex前提であることが調査で判明した。本節はリポジトリ読解に加え、実際のrun
ディレクトリの記録と実測により確認した。以下では実測済みの事実を「実測確認済み」、
コード読解から導いた未実測の挙動を「読解確認」と明記し、推測と区別する。

### 確認済みの非対称一覧(優先度順)

#### 実行役側

1. **最優先: read-only Claudeが検査を実行できない(実測確認済み)。**
   `src/cross_harness/runner.py`の`_claude_command`はwrite=falseで
   permission-modeをmanualにする。headless実行では承認を要するコマンドが拒否
   されるため、Claudeロールのtesterとsecurity_reviewerはプロジェクトの検査を
   実行できない。両ロールをharness=claudeにした実測では、検査を実行しないまま
   successを返した。これは誤った成功報告を生む。
2. **watchがClaudeの作業詳細を表示しない(読解確認)。**
   `src/cross_harness/watch.py`の`format_event`は`item.`で始まるイベント型だけを
   詳細化する。Claudeのstream-jsonではtype名だけが並び、実行コマンドと変更
   ファイルをwatchから確認できない。実行中の監査可能性が下がる。
3. **要約がClaudeのtool失敗を検出しない(読解確認)。**
   `src/cross_harness/summarize.py`の`parse_events`はcommand_execution項目だけを
   コマンド失敗として扱う。このためClaudeのtool_useとtool_resultの失敗を拾わず、
   失敗したテストをsuccessと報告しうる。
4. **Claudeのrate limitと認証失敗を正しく終端できない(読解確認)。**
   `src/cross_harness/runner.py`のRATE_LIMITとAUTH_FAILUREはCodexの文言を前提に
   判定する。一方Claudeはレート制限をrate_limit_eventという構造で通知するため、
   blockedにならずretryされる。この項目も誤った成功報告または誤った再試行を
   生むため、(1)とともに最優先とする。
5. **Claude設定の課金・接続先を検査しない(読解確認)。**
   `src/cross_harness/auth.py`には`verify_codex_config_ownership`があるが、Claude側
   に相当する検査がない。Claude設定ファイル経由のAPI課金や外部ルータへの切替を
   無検査で許すため、サブスクリプション利用という前提を保証できない。
6. **timeout後のClaude resume情報を失う(読解確認)。**
   `src/cross_harness/summarize.py`の`parse_events`は終端のresultイベントからのみ
   Claudeのsession_idを取得する。全イベントにsession_idが含まれるにもかかわらず、
   timeoutで中断するとresumeできない。
7. **Claudeのwriteロールを作業ディレクトリに拘束しない(読解確認)。**
   `src/cross_harness/runner.py`のClaude起動経路はCodexのsandbox指定に相当する
   作業ディレクトリ拘束を渡さない。worktree分離時でも元リポジトリへ書けるため、
   分離と既存変更の保護を損なう。
8. **Claudeの役割定義が不足する(読解確認)。**
   `.claude/agents/`にはimplementer、tester、debugger、security_reviewerに対応する
   Claudeエージェント定義がない。ロール別の実行契約がClaude側では具体化されない。
9. **委譲先Claudeに実行役憲章がない(読解確認)。**
   委譲されたClaudeはClaude側の`CLAUDE.md`を読み、そこにある「自分は
   orchestratorである」「EditとWriteでプロジェクトコードを編集しない」という
   指示役の規則に従う。これは実行役として与えられる役割と編集権限に矛盾する。
   Claude側に実行役向け憲章がないことが問題の本質である。
10. **Codex resumeがsandbox指定を落とす(読解確認)。**
    `src/cross_harness/runner.py`のresume用Codex起動経路では初回起動時のsandbox
    指定を再適用しない。再試行後だけ権限制約が初回と異なり、実行条件の一貫性を
    保てない。

#### 副次的な非対称

- `src/cross_harness/runner.py`ではCodexのfinal.jsonを出力スキーマで強制する一方、
  Claudeのfinal.jsonはイベント後のパースで作る。結果形式の保証と不正な最終応答の
  検出強度が異なる。
- doctor、inventory、trustはCodexのみを手厚く扱う。該当する運用診断がClaudeには
  なく、障害時の自己診断範囲が非対称である。
- `config/default.toml`のClaudeロールは全てretries=0である。retryと
  escalationに到達せず、設定上の復旧経路を検証できない。
- `README.md`冒頭は一方向の記述のままであり、利用者が双方向設定の範囲と制限を
  誤認しうる。

#### 指示役側

- `src/cross_harness/config.py`ではparent_harnessを検証するのみで、実行時には消費
  しない。設定値によって親の振る舞いを切り替えられない。
- `src/cross_harness/runner.py`のCROSS_HARNESS_PARENTは固定値であり、参照する箇所が
  ない。親ハーネスの実態を子へ伝える契約になっていない。
- `src/cross_harness/hooks.py`の`codex_pre_tool_use`は文脈を判定せず、Claudeへの
  委譲を無条件に拒否する。Codexを正規の指示役にする経路を塞いでいる。
- Codex側の資産は実行役専用であり、Claudeのorchestrator skillに相当する指示役用
  資産が存在しない。したがって、Codexを指示役にする対応は未実装である。

### 段階計画

#### フェーズA: 実行役の対称化を先行する

実行役の(1)から(10)を順に是正し、Claudeのstream-jsonをwatchで詳細表示できるよう
にする。(1)のread-only検査実行と(4)のrate limit・認証失敗判定は、誤った成功報告を
生むため、他の項目に先行して完了させる。次に要約・session resume・作業ディレクトリ
拘束・設定所有権検査を整え、Claudeの役割定義、憲章の分離、Codex resume時のsandbox
維持を扱う。

完了条件は、両harnessのtesterとsecurity_reviewerが実際に検査を実行し、その成功・
失敗・rate limit・認証失敗が同じ意味のsuccess、failed、blockedへ記録されることとする。
watchとsummaryには両形式のコマンド、変更ファイル、tool失敗が残り、timeout後も
sessionをresumeできることをrun記録で確認する。writeロールはworktree外へ書けず、
各対応Claudeロールは実行役専用の指示で動作し、Codexの再試行も初回と同じsandboxで
動作することを完了条件とする。

#### フェーズB: 指示役の対称化

フェーズAの実行契約が揃った後、hooksに親・子・通常操作を区別する文脈判定を入れ、
Codex向けorchestrator資産を整備する。あわせてparent_harnessを実際の起動・環境・
制御フローで消費し、固定値のCROSS_HARNESS_PARENTを実際の親に一致させる。

完了条件は、ClaudeとCodexのどちらをparent_harnessに選んでも、同一の役割・制約・
委譲深さで正規の子実行を開始できることとする。hookは委譲された子からの入れ子起動
だけを拒否し、指示役からの正規委譲を拒否しない。親ハーネス値はrun記録と子環境で
一致し、両指示役が対応するorchestrator資産を用いて同じ完了判定と停止規則に従うことを
確認する。
